# 公开首页与版本更新规则

本文件是 Legal OS 公开仓库的首页、版本文案和公开更新的唯一操作规则。

核心原则只有一句：**README 是产品入口，不是内部发布台账。**

## 1. 文件职责与事实来源

| 文件 | 对外职责 | 可以写什么 | 不应写什么 |
|---|---|---|---|
| `legalos.manifest.json` | 机器可读的公开包事实源 | 公开版本、发布状态、Skills、路由、模板运行时、质量门 | 面向用户的解释性长文 |
| `README.md` | 产品首页与首次使用入口 | 产品定位、用户价值、能力、安装、示例、边界、文档导航 | 内部路径、PR/commit、审计过程、候选协调、私有 overlay |
| `CHANGELOG.md` | 历史变化索引 | 每个版本的功能、修复、边界变化和验证摘要 | 尚未授权的发布结论、客户事实 |
| `RELEASE_NOTES_vX.Y.Z.md` | 单个版本说明 | 版本范围、升级提醒、已知限制、公开迁移说明 | README 首页宣传文案 |
| `TEST_REPORT_vX.Y.Z.md` | 可复核的验证记录 | 命令、结果、环境、失败与限制 | 把测试数字写成产品能力承诺 |
| `OPEN_SOURCE_BOUNDARY.md` | 公私边界与安全说明 | 公开包范围、禁止进入公开仓库的材料、外部动作边界 | 具体客户、内部项目路径或事项事实 |
| `CONTRIBUTING.md` | 贡献入口 | 提交要求、公开安全、审查步骤和本规则链接 | 版本发布台账 |

事实冲突时，按以下顺序处理：

1. 先修正 `legalos.manifest.json` 或对应的机器可读源；
2. 再同步 README、CHANGELOG 和版本文档；
3. 最后运行公开文档校验和仓库质量门。

README 不得反过来定义版本、包清单或发布状态。

## 2. README 的固定结构

每次重写或新增首页内容，保持下面的顺序，不把发布过程插入产品叙事：

1. **首屏**：名称、一个明确定位句、最多三枚事实型 badge、文档入口；
2. **当前版本**：只写公开版本和成熟度，例如“v0.7.0 公开预发布版”；
3. **它解决什么问题**：面向使用者的结果，不描述内部组织方式；
4. **核心能力**：按工作结果或场景分组，必要时链接到能力矩阵；
5. **工作方式**：一张简洁流程图或四到六步说明；
6. **快速开始**：最短可复制安装命令和最小调用示例；
7. **使用示例**：三到五个真实但不含客户事实的请求例子；
8. **边界**：法律判断、事实核验、外部动作授权和公开安全边界；
9. **文档导航**：架构、能力、模板、测试、变更和贡献入口；
10. **许可证与版本链接**：只保留当前状态，不保留过期候选文案。

首页要让第一次访问的人在一分钟内完成三件事：知道项目是什么、判断是否适合自己、知道下一步怎么安装。

## 3. 首页禁止出现的内容

以下内容必须放到 Release Notes、TEST_REPORT、CHANGELOG 或治理文档中，不能写进 README 的产品主体：

- PR 编号、commit hash、GitHub Actions 运行记录、CodeQL 记录；
- “本地验收”“公开边界复核”“内部定稿”“候选协调”等过程性表述；
- `release_status`、内部 manifest 字段名、私有路径和本机目录；
- 客户、案件、真实姓名、内部事项、私有 overlay 或未公开模板；
- 把“去身份化”“脱敏处理”等内部清理动作当作产品卖点；
- 尚未核验的性能、胜率、节省时间、覆盖率或质量承诺；
- 与当前 manifest 冲突的旧版本、RC、候选或“上一版本”说法；
- 只对维护者有意义、但不能帮助用户开始使用的内部术语。

“14 个 Skills”“12 条路由”“24 个标准 Office 模板”这类可由仓库事实直接核验的包清单可以保留，但必须由校验器确认，不手工猜数。

## 4. 版本更新规则

### 4.1 功能或能力变化

1. 先更新实际 Skill、脚本、模板或 manifest；
2. 更新 `legalos.manifest.json` 中的公开包清单、路由或版本；
3. 更新 README 的能力摘要和对应文档链接；
4. 在 CHANGELOG 和版本说明中记录变化、边界和迁移影响；
5. 只有仓库中存在真实实现、资源和测试时，才能在首页宣称该能力。

### 4.2 版本状态变化

版本状态只在机器可读源、CHANGELOG、版本说明和 README 四处形成一致投影：

- **本地草稿**：只在本地工作树，README 不写成已发布；
- **公开候选**：可以在 Release Notes 说明候选性质，首页只写“公开预发布版”或明确的候选提示；
- **已发布公开预发布版**：manifest、README、CHANGELOG 和 Release 对应同一版本；
- **稳定版**：只有明确经过稳定版决策和发布授权后才可使用“稳定版”；
- **撤回/阻断**：先更新机器可读状态和版本说明，再从首页删除过期宣传，不静默抹掉历史记录。

“manifest 的 `released`”表示该公开版本已经完成发布记录，不等于产品成熟度为 stable；首页必须把“发布状态”和“成熟度”分开表达。

### 4.3 安全、隐私和边界变化

安全边界、公开包清理、依赖和验证器变化记录在 `OPEN_SOURCE_BOUNDARY.md`、CHANGELOG、TEST_REPORT 或 SECURITY 中。README 只保留用户必须知道的结论，不展开内部扫描过程。

## 5. 每次更新的固定顺序

按下面顺序执行，任何一步失败都不得继续发布：

1. **范围确认**：写明是文案、能力、规则、模板、依赖还是版本状态变化；
2. **源文件修改**：先改真实实现和 manifest，再改 README；
3. **公开边界检查**：扫描私有路径、客户事实、秘密、内部术语和过期状态；
4. **一致性检查**：校验版本号、Skills 数量、路由、模板数量、链接和安装入口；
5. **行为验证**：运行仓库 validator、路由测试、安装 dry-run 和受影响测试；
6. **人工首页审阅**：只问“新用户能否快速理解并开始”，不把内部验收报告复制到首页；
7. **本地验收记录**：把命令和结果写入 TEST_REPORT 或工作记录；
8. **外部发布**：只有得到单独明确授权后，才执行 push、tag、Release 或其他外部写入。

推荐的最小本地门禁：

```bash
python3 scripts/validate_public_surface.py
python3 scripts/validate_repo.py
python3 scripts/validate_routing_scenarios.py
python3 -m unittest discover -s tests -v
./install.sh --dry-run
```

普通法律 Word/DOCX 不是本规则的首页发布门禁对象；除非用户明确要求视觉交付或源文件出现具体版式风险，不得因为预览渲染把公开文档发布流程拖成视觉流程。

## 6. 提交前人工清单

- [ ] 首屏是否只包含产品定位、事实 badge 和用户入口？
- [ ] 是否删除了 PR、commit、Actions、内部路径和审计过程？
- [ ] README 的版本和成熟度是否与 manifest、CHANGELOG、Release Notes 一致？
- [ ] Skills、路由和模板数量是否由仓库实际内容核验？
- [ ] 所有能力宣称是否能在公开包中找到实现、资源和验证？
- [ ] 是否没有客户事实、真实材料、私有 overlay、秘密或内部姓名？
- [ ] 安装命令和至少一个最小示例是否可复制？
- [ ] 法律边界和外部动作授权是否清楚？
- [ ] 变更是否有对应的 CHANGELOG、版本说明或测试记录？
- [ ] 是否尚未获得授权就准备推送、打 tag、发布或发送？

若发现首页需要解释“为什么这样发布”而不是“用户如何使用”，应把内容移出 README，而不是继续堆叠首页。
