# Legal OS Contract Workspace

## 当前边界

合同能力是 `tool-assisted-pilot`，不是无人值守法律服务；具体运行环境和编排由使用者自行决定，本 Skill 不绑定特定运行方式。旧 Frozen 文档只作治理与规则来源，不代表真实合同结果已通过端到端验证。

公开包提供 `redline_metrics.py` 诊断脚本和 `redline_quality_gate.py` 硬门。它不包含组织内部的审批系统、现行法数据源、发送能力或 Final 发布授权。

## 必须组合使用

- 修改 DOCX 时检查 OOXML、文本、字体属性、段落属性、编号、表格、页眉页脚、批注和修订结构。交付前执行 [redline-quality.md](references/redline-quality.md) 的秒级源文件校验。
- 修订交付前运行本 Skill 的 `scripts/redline_quality_gate.py`；`scripts/redline_metrics.py` 只作诊断。
- Office 源文件优先并实行条件式视觉 QA：先执行统一入口的 [office-source-policy.md](../legal-os-unified-intake/references/office-source-policy.md)。源文件结构、文字、修订和格式属性始终是主 Gate；普通和正式法律 DOCX 均不因“可直接使用”而自动渲染，仅在用户明确要求、交付物本身为视觉型文件或源文件检查发现具体版式风险时做一次定向检查。用户明确说不渲染时是硬停止。历史路径 [no-render-policy.md](references/no-render-policy.md) 仅作兼容指针。
- 需要现行中国法时使用可核验的权威研究能力；合同事实只来自当次材料。
- 标记为外部 Final 前，另行执行组织适用的法律质量门、签核与授权流程。

## 受控工作流

1. 建立 matter manifest：登记事项、我方立场、阶段、风险、输出意图、全部文件版本和原件 SHA-256。原件只读，派生文件另存。
2. 读取合同、附件、报价、澄清、补充协议及履行材料；不同版本不得静默合并，缺失事实保持待核验。
3. 建立交易模型与付款—交付—验收—质保—违约—解除闭环，只加载触发的问题域。
4. 形成事项级 negotiation policy。比例、期限、责任上限等商业参数必须来自用户当次指示、事项材料或已批准策略；不得使用隐藏全局默认值。
5. 先确定目标修订文字，再使用支持真实 Word 修订痕迹的工具生成字符／词语级修订。人工 `old/new` 整句替换只能是临时中间态。
6. 批注仅用于根据现有材料无法直接确定、必须由用户确认事实或作出商业决策的事项；批注范围限定为影响合同签署、付款、验收、责任承担等核心事项的少量关键待确认项，其他事项一律列入内部审核报告，不添加批注。一般文字修订、风险收窄、表述优化及保护性条款新增均不加批注，仅以修订痕迹体现。每条批注只处理一个待确认事项，必须锚定最小必要正文范围，仅用一句明确短句提问，不写背景、原因、法律分析、风险展开或处理方案。批注原则上不超过 30 个中文字符，超过 30 字提示优化；超过 50 字、无正文锚点、范围批注 start/end ID 不平衡、同时包含多个事项（仅标点/并列词不构成 FAIL，须命中两个及以上问号、两个及以上"是否"或重复"请确认/需确认"、"分别确认/另请确认/同时请确认/还需确认"、或"1/2、A/B、第一/第二"枚举等明确多事项模式才 FAIL），或对一般修改/新增段落添加批注时，质量校验直接 FAIL。锚定后不得继续替换同一段文字。
7. 运行红线硬门；任一错误只能保留 Draft。根据法律影响复核重大修改，不按修订字符长度增加审批或台账。
8. 完成内容、金额、OOXML、可访问性及隐私检查，并完成秒级基础校验：原文件未被覆盖、文件可正常打开、修订痕迹存在、修改范围符合指令、拒绝修订后的视图与原件一致、接受修订后的视图可读取且关键法律文字经主审或指定复核人复核。只有公开脚本 `PASS`、退出码 `0`，秒级基础校验通过，且组织要求的签核匹配当前文件哈希时，才可标 Final。完成后直接交付修订版 Word。
9. 用户纠正或运行缺陷只有在语义查重后确认属于净新增、需替换、收窄、合并或删除的系统规则时，才保留最小 Learning Candidate 并交 `legal-os-learning-maintenance`；现有规则已充分覆盖的观察直接丢弃，不记录重复描述。普通合同任务不得因此加载维护 Skill，也不得自动改写全局规则或绕过质量门。

详细标准见 [redline-quality.md](references/redline-quality.md)。

## 逐字逐句硬规则

- 能改一字，不改一句；能改一句，不改一段。未变化文字不得进入 `w:del`／`w:ins`。
- 原文缺少必要机制，或局部修补无法形成完整可执行条款时，可以整句或整段新增。
- 修订颗粒度取决于实际法律和文字需要，不以字符长度触发台账或审批。原文已有同一机制时，应优先局部修改；原文缺失必要机制时，可以新增完整句段。
- 修订作者默认“法务”。`redline_metrics.py` 仅作诊断，正式红线完整性结论只认 `redline_quality_gate.py`。

## 必跑命令

```bash
python scripts/redline_metrics.py REDLINE.docx

python scripts/redline_quality_gate.py \
  --original ORIGINAL.docx --redline REDLINE.docx \
  --out-json REDLINE_REPORT.json
```

## 默认输出

- 默认只交付用户明确要求的核心 Word；审核结论和待核事项在完成消息中简述，不默认另制内部审核报告。
- 用户要求修订版时只交付修订版；清洁版仅在用户明确要求时生成。保留原结构、编号、表格和版式。
- Final：仅限签核哈希、用途和风险等级完全匹配的版本；发送、签署、提交或发布仍需单独授权。

## 硬停止

- 我方立场、关键版本、付款／验收／权利处分材料存在核心冲突；
- 需要现行法律但未核验，或正式事项观点无可核验来源；
- 原文拒绝本次修订后的视图与源合同不一致；
- 接受修订后的视图无法读取，或关键法律文字复核不通过；
- 秒级基础校验未通过；
- 批注超 50 字、无正文锚点、范围批注 start/end ID 不平衡、批注命中明确多事项模式（两个及以上问号、两个及以上"是否"或重复"请确认/需确认"、"分别确认/另请确认/同时请确认/还需确认"、"1/2、A/B、第一/第二"枚举），或对一般修改/新增段落添加批注；
- `redline_quality_gate.py` 退出码非 `0`；
- 组织要求的外部发布签核或授权未完成。
